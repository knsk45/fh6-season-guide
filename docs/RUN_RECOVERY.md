# Надёжный запуск FH6

## Источник текущей задачи

Первое действие каждого heartbeat или ручного обновления — `python automation/refresh_guard.py start`, после сокращения истории — `python automation/refresh_guard.py status`. Использовать доступный Python 3; в текущем окружении он есть в bundled runtime Codex. Эти команды не запускают сборку.

`automation/runs/refresh/active.json` содержит текущую задачу, независимый `runId`, этапы, причины остановки и `nextAction`. Снимок каждого запуска и журналы сохраняются в одноимённом подкаталоге. Каталог исключён из Git. OS-lock не допускает параллельное исполнение команд guard и освобождается при аварии процесса.

Команда `status` только читает атомарный снимок и доступна даже во время работающего executor. Временная блокировка переименования файла Windows/OneDrive повторяется ограниченное число раз; прежний корректный checkpoint не уничтожается. При постоянной ошибке запуск не считается успешным, а независимый HA-контроль продолжает работать.

Незавершённый запуск возобновляется с тем же ID, а не заменяется новым. Старые пользовательские сообщения в истории — контекст, не новый запрос. Явное новое указание пользователя имеет приоритет; при отмене сохранить причину остановки, не заявлять об успешном обновлении. После compaction сначала перечитать active.json, затем продолжить текущий запуск. Вопрос пользователя по ходу работы не означает автоматическую отмену обновления.

## Аудит и исполнение

1. Выполнить живой аудит по SKILL.md и записать dated section в SOURCE_NOTES. Не использовать список галочек как доказательство исследования.
2. Подготовить локальный `audit.json`: `checkedAt`, `seasonConfirmed`, точный `seasonEndAt`, массив `sources` с каждым `requiredSources.id` ровно один раз (`id`, `status`: checked/unavailable/no_current_item, `checkedAt`, `url`, `note`), массив `visuals` для каждой activity (`id`, `sha256` файла, `note`), `sourceNotesSha256`.
3. `python automation/refresh_guard.py audit --input <audit.json>` проверяет полноту, срок давности до четырёх часов, текущий сезон и отпечатки. Фиксирует состояние и проектные настройки. При изменениях карточек/источников/визуалов до сборки повторить соответствующий аудит и регистрацию.
4. `python automation/refresh_guard.py execute` выполняет этапы с записью фактических exit codes и журналов. На восстановлении до доставки безопасно повторяет детерминированные проверки и сборку; publisher и уведомление идемпотентны. При уже подготовленном финале повторяет только недоставленное уведомление/HA receipt, а не публикацию.
5. Сборочный preflight проверяет штатный legacy `deliver_portable_artifact.mjs`. Его отсутствие блокирует полное обновление до изменения публичной даты. Не создавать поддельную замену и не объявлять другую проверку штатной. Если сборка частично изменила отчёт, publisher не запускается до восстановления корректного отчёта.
6. Проверка успеха требует аудит, все этапы сборки, STRUCTURE_OK, PUBLISHED_SHA/PAGES_URL, публичный Steam и метрики текущего RunId. Отсутствующий этап, изменённый журнал или изменённые входные данные дают BLOCKED, а не COMPLETED.
7. `result.json` — единственный текстовый итог для HA и чата. `summary.txt` добавляет подтверждение доставки. Завершать ответ по сохранённому результату; не заменять итог ответом на старое сообщение. После завершения обновить automation memory.

`lastContentUpdate` остаётся датой успешной проверки сводки. Guard RunId обозначает попытку целиком и не зависит от этого timestamp; один и тот же ID используется для метрик, уведомления и HA receipt. Незаполненный/недоступный источник явно отражается в аудите, а не подменяется старыми данными.

## Независимый контроль HA

`ha_refresh_watchdog.ps1 -Action Install` сохраняет резервные копии только двух настроек, создаёт/обновляет `fh6_refresh_receipt` и `fh6_refresh_watchdog`, перечитывает их, включает и проверяет конфигурацию. Не затрагивает существующий `input_boolean.fh6_online`.

После успешной отправки итогового уведомления guard посылает авторизованное событие `fh6_refresh_finished`. HA принимает только итог текущего дня после 06:00 с нужным project/status и подтверждением уведомления. После этого guard проверяет `last_triggered` automation-получателя. BLOCKED/PENDING_CONFIRMATION — тоже полученный итог, но не успешное обновление сводки.

Watchdog в 06:30 Asia/Krasnoyarsk проверяет получение итога. Повторная проверка каждые 5 минут позволяет обнаружить пропуск после перезапуска HA. Предупреждение — не более одного за день, независимо от доступности Codex/ноутбука. Нужен работающий сервер HA и его мобильный канал; абсолютная гарантия доставки не предполагается.

`-Action Test` проверяет настоящим HA Jinja-движком: до дедлайна, пропущенный итог, полученный итог, подавление повторов и позднее восстановление. Не отправляет тестовую тревогу и не меняет отметку настоящего запуска. `-Action Check` проверяет включение обеих automation. Никогда не посылать фиктивный production receipt ради теста.

При проблеме финальной доставки run остаётся `AWAITING_DELIVERY`. Повторить `execute` для доставки/receipt, не создавать новый запуск. При смене календарного дня требуется отдельно закрыть старую недоставленную попытку как ошибку и начать новый аудит; старый receipt нельзя считать сегодняшним.
