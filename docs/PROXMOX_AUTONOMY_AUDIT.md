## Вывод

Основа уже есть: CT109 может запускать Codex CLI самостоятельно. Ноутбук не является необходимым участником.
`automation/server/runner.py` вызывает Codex под пользователем `fh6-editor`, принимает редакторский кандидат
и передаёт его издателю `fh6` через существующий guard. Нужен работающий серверный редактор и завершённая
обработка исключений; перенос сборки в GitHub Actions или второй независимый publisher не требуется.

«Замкнуть на Proxmox» означает запуск, состояние, проверки и публикацию на сервере; модель Codex всё равно
требует доступ к OpenAI. Локальная работа без интернета здесь не реализована.

## Подтверждённые ограничения кода

1. **Серверный редактор зависит от авторизации и реального выполнения Codex.**
   `codex login status` проверяется перед запуском. При ненулевом exit code сохраняется `AUTH_REQUIRED`.
   Даже наличие credentials не доказывает доступность модели, лимит или успешный live web search.
   После входа необходим настоящий запуск через панель и проверка итогового guard result.

2. **Смена сезона пока отвергается supervisor.**
   В `runner.run()` сравнивается весь объект `season`; любое отличие создаёт review-required и не применяется.
   Это касается даже исправления метаданных. Редактору предложено выполнять rollover в изолированной копии,
   но `safe_candidate()` переносит только state/SOURCE_NOTES/audit/new-season-input и assets, а не `data/history`
   и `seasons`. Поэтому простое удаление запрета уничтожит гарантию сохранения архивов.
   Нужен отдельный проверяемый путь rollover на стороне издателя: валидировать вход, подтвердить новый сезон
   live, сохранить прежнее состояние/архив, применить assets и обновить sparse-checkout для новой папки.
   Существующие `start_new_season.ps1` и guard следует использовать, а не обходить.

3. **Steam approval ещё не исполняется автоматически.**
   Панель сохраняет SHA двух текстов со статусом `AWAITING_BROWSER_PUBLICATION`. В серверном supervisor
   нет потребителя, который открывает авторизованный Steam, заменяет разделы и выполняет mark/check.
   Это разрешение на будущую замену, а не запись об уже опубликованном тексте. Повторный вход в Steam,
   Steam Guard и ошибки интерфейса потребуют владельца. Не менять существующее правило подтверждения
   и не использовать неофициальные write endpoints.

4. **Автоматического повторного редакторского аудита после BLOCKED в тот же день нет.**
   `runner.run()` без `--force` пропускает дневной `BLOCKED`, если `finishedAt >= 06:00`.
   Доставка повторяется отдельно, но неудачный поиск/лимит/авторизация сами по себе не запускают новый поиск.
   Сейчас повтор можно запросить кнопкой панели. Для автоматического восстановления нужен ограниченный
   retry с классификацией причины, cooldown и дневным лимитом; нельзя повторять всю публикацию из-за HA.

5. **Прежний editor audit может попасть в новый workspace.**
   `editor()` копирует repo, исключая `.git`, runs и несколько служебных имён, но не
   `automation/editor-audit.json`. Этот файл переносится в canonical после предыдущей успешной проверки.
   При повторе в пределах четырёх часов прошлый аудит может удовлетворить freshness-проверке, если
   остальные входы прежние. Нужно исключать старый handoff и привязывать новый к конкретной попытке,
   не разрешая признавать наличие файла свежей работой редактора.

6. **Диагностика редактора недостаточно подробна.**
   Любое исключение даёт общий `FAILED`, часто без причины для владельца. Exit 0 показывает завершение
   CLI, а не наличие принятого audit. `editor.log` перезаписывается; прежние workspaces архивируются,
   но лог не привязан к RunId. Нужны отдельные статусы: auth, timeout, inference error, missing audit,
   audit rejected, rollover pending; безопасные метаданные и журнал каждой попытки.

7. **Нет явной синхронизации перед аудитом.**
   Publisher делает fetch и отказывается публиковать, когда HEAD не содержит удалённую ветку,
   но supervisor не выполняет предварительный безопасный fast-forward. Изменения из облачного Codex
   могут привести к расхождению. Нужен чистый checkout + fast-forward до чтения state; dirty/diverged
   состояние должно останавливаться без reset, force-push или потери серверных изменений.

8. **Публичная история метрик обновляется после сборки/публикации.**
   В guard этап `metrics` стоит после `publish`. Скрипт метрик меняет `data/publication-metrics-history.json`,
   но повторного рендера и публикации истории в этом запуске нет. Поэтому текущая точка графика может
   появиться лишь при следующей сборке. При изменении порядка сохранить единственный RunId и baseline;
   считать это отдельным исправлением, не скрытой повторной ежедневной публикацией.

В `data/current-season.json` записано `lastContentUpdate=2026-10-10T06:00:53+07:00`.
Последний найденный Pages deployment от 12.10.2026 успешен и связан с исправлением панели входа.
Успех публикации кода панели не доказывает ежедневный аудит 11–13 октября. Это повод получить

исключены из Git, поэтому по репозиторию их состояние установить нельзя.

## Порядок завершения

1. Получить read-only snapshot CT109 и сравнить серверный commit с анализируемой версией.
2. При необходимости завершить device login в панели; выполнить один настоящий ручной запуск.
   Подтвердить новый audit, пройденные этапы, публикацию, два Steam-check, метрики и HA receipt.
   Не объявлять весь цикл успешным, если результат — BLOCKED/PENDING_CONFIRMATION.
3. Исправить жизненный цикл editor audit, журналирование и ограниченный retry. Не расширять права редактора.
4. Реализовать серверный rollover с сохранением истории, месячных оригиналов и sparse assets;
   проверить границу четверга на изолированных fixtures. До этого пятничный переход остаётся ручным.
5. Добавить исполняемый Steam-процесс после конкретного SHA-подтверждения владельца, с публичной проверкой
   обоих разделов перед mark/check; неподтверждённые или изменившиеся тексты остаются pending.
6. Уменьшать объём Codex постепенно: обычным Python извлекать структурированные факты и дельты источников,
   кэшировать байты неизменившихся плиток, передавать компактный контекст. Пока проект требует полный
   ежедневный аудит всех источников/визуалов, нельзя отключать его только из-за совпадения HTTP-хешей.
   На rollover, противоречия, решения, переводы и содержательную проверку изображений оставлять Codex.

## Диагностика без запуска конвейера

Добавленный `automation/server/diagnose.py` читает только разрешённые поля и локальные статусы.
Не читает auth.json/HA credentials, не печатает логи, токены, raw errors, device codes или свободный
текст сообщений. Не запускает inference, guard, publication, notifications, service restart или сеть.
`CREDENTIALS_PRESENT_NOT_LIVE_VERIFIED` означает только exit 0 локальной команды login status.

После размещения файла в CT109:

```sh
python3 /opt/fh6/repo/automation/server/diagnose.py
```

Из root-консоли Proxmox:

```sh
pct exec 109 -- python3 /opt/fh6/repo/automation/server/diagnose.py
```

Полученный JSON достаточен для следующего технического шага. Не пересылайте полный editor.log,
auth.json, параметры HA или одноразовый device code. При необходимости разбирать log следует внутри CT109.

Проверки добавлений:

```sh
python3 automation/server/test_diagnose.py
```

Обязательная регрессия при последующих изменениях build-chain:
`test_portable_report.py`, `test_refresh_guard.py`, `server/test_server.py` и отдельный browser QA.
В этой ветке production pipeline, state, расписание, правила Steam и секреты не изменены.

## Официальные возможности Codex

- [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode): `codex exec` применяется
  в скриптах и scheduled jobs, переиспользует сохранённую авторизацию, поддерживает JSON events/schema.
- [Authentication](https://learn.chatgpt.com/docs/auth): device login для headless сервера выполняется
  владельцем через браузер; credentials остаются в приватном home серверного редактора.

Отдельный оплачиваемый API не является обязательным условием восстановления существующей схемы.
Доступность модели, лимиты аккаунта и сети необходимо проверить реальным серверным запуском.
