# Автоматическое восстановление FH6

Supervisor остаётся единственным издателем в CT109. Новый timer проверяет состояние
каждые пять минут и после перезагрузки; он не запускает второй конвейер рядом с
работающим `refresh`, `manual` или recovery. Используются существующие OS-lock
runner и guard. Проверяется именно ActiveState, включая `activating`.

## Что повторяется

- Сетевые ошибки, HTTP 429/500/502/503/504 и timeout получают паузы 5, 15 и
  60 минут, максимум три дополнительных запуска за календарный день Красноярска.
  Интервал проверки timer может добавить до пяти минут к указанной паузе.
- Оборванный RUNNING возобновляется, только если службы не работают и обе
  блокировки свободны. Существующий guard сохраняет RunId незавершённой попытки.
- Потеря авторизации не расходует модель на бесконечные попытки: timer проверяет
  новый CONNECTED в login bridge после ошибки и exit code `codex login status`,
  подавляя весь вывод. Одного наличия прежних credentials недостаточно. После
  входа владельца через панель планируется ограниченный повтор; пароль/OTP вводит владелец.
- При наличии свежего принятого guard-аудита с прежними входами повторяются
  детерминированные этапы guard, без нового Codex. Старый итог BLOCKED не меняется:
  guard создаёт новую попытку. При устаревшем/изменённом аудите нужна новая проверка
  Codex. Срок четыре часа, источники, сезон, хеши и receipt не обходятся.
- Получение каждой исходной страницы делает до двух коротких повторов при
  временных ошибках (2 и 5 секунд); 404 не повторяется. Это всё ещё
  NOT_REVIEWED, а не редакторский аудит.
- Timeout останавливает всю группу процессов вызова Codex, включая потомков
  runuser. Предыдущие editor/validation журналы сохраняются в приватном
  `/var/lib/fh6/editor-logs`; workspaces по-прежнему архивируются.
- Старый `editor-audit.json` не копируется в новый workspace. Exit 0 без нового
  файла получает NO_AUDIT. ACL чтения кандидата восстанавливается при каждом
  handoff; успешный handoff удаляет устаревший review-required marker.

## Где требуется владелец

Структурные ошибки, неизвестные причины, неготовый rollover и непроверенные
данные получают NEEDS_REVIEW. Никакие команды из логов не исполняются, исходный
код автоматически не переписывается, секреты/роутер/права других служб не меняются.
PENDING_CONFIRMATION, COMPLETED и AWAITING_DELIVERY не запускают новый аудит.
Доставка уже сохранённого финала остаётся за отдельным `fh6-delivery.timer`.
Steam-публикация требует прежнего подтверждения и публичной проверки.

Общий дневной счётчик хранится атомарно в `/var/lib/fh6/recovery.json`; он не
сбрасывается при появлении нового RunId или перезагрузке. После трёх попыток
показывается LIMIT_REACHED. Следующий штатный дневной запуск не блокируется;
ручная кнопка панели остаётся доступна. Старые терминальные запуски прошлого
дня автоматически не переигрываются. Панель показывает ожидание, время следующей
попытки, необходимость входа или проверки; диагностический JSON содержит только
разрешённые статусы, фиксированную причину и счётчик, без текстов логов/credentials.

## Установка на существующий CT109

`automation/server/install_recovery.py` — самостоятельный установщик из этой
ветки. Он работает только от root на fh6-collector, проверяет точные SHA-256
прежних файлов, сохраняет резервные копии и владельцев/режимы. При неизвестной
версии или работающем конвейере отказывается от установки. Код ставится под
блокировками, тестируется в изолированных fixtures, затем включается timer и
перезапускается панель. Ошибка проверок откатывает файлы; сборка/публикация,
новый вызов Codex и тестовый HA receipt установщиком не запускаются.

Проверки включают policy/execution recovery, серверную панель, разрешения
серверных пользователей, диагностику, refresh_guard и portable build. Перед
установкой убедиться по выводу, что штатный daily/manual запуск завершён.

Новая установка включает этот timer через cutover.sh вместе со штатными таймерами,
после проверки миграции и отключения второго издателя.
