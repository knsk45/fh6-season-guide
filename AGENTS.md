# FH6 project instructions

- For every Festival Playlist refresh, season rollover, report repair, or scheduled run, use the repo skill `$fh6-season-maintainer` from `.agents/skills/fh6-season-maintainer/`.
- Treat `data/current-season.json` as the only editable source of current-season card content, ordering, deadline, visuals, completeness, and missing fields.
- Treat `data/project.json` as the persistent source for project-wide content. Its branding assets and enabled visit analytics must remain linked from the public HTML. The visit counter stays inside the final support block. The enabled support block must remain at the end of `README.md` and `reports/current-week.html`, and must never be counted as a Festival Playlist card.
- Check every entry in `data/project.json.requiredSources` on every refresh. Record the result in `reports/SOURCE_NOTES.md`; a source with no current-week publication is a checked absence, not permission to reuse old data.
- On every refresh, audit `visual` for every activity even when it is absent from `openItems`. Prefer the exact current-week game tile; otherwise use a distinct activity-specific current-week screenshot or clearly labelled derivative from the current season overview. A shared fallback must remain temporary, must not count as a completed visual, and must be replaced as soon as current-week evidence exists. Never reuse a prior-week visual.
- After every successful complete daily source audit that confirms the active season, refresh `lastContentUpdate` to the current `Asia/Krasnoyarsk` time even when no card fact changed, then regenerate, validate, and publish the report. Do not refresh it when the live season or required-source audit could not be confirmed.
- Treat the current file in `seasons/`, `CURRENT_WEEK.md`, `reports/artifact.json`, and `reports/current-week.html` as generated outputs. Regenerate them; do not hand-edit their duplicated content.
- Never hardcode a universal card count. Read `season.expectedCardCount` and `season.expectedDailyItems` from the current state.
- Keep performance class and PI restrictions as plain text in season state. The report builder decorates D/C/B/A/S1/S2/R/X plus three digits as game-style badges; validation must reject missing badge conversions.
- Every specifically recommended vehicle must include its four-digit model year. Show tune share codes without tuner names. Keep all hyperlinks in `sourceHtml`, never inside `conditionHtml`, `howHtml`, or `tuneHtml`; every card link must use `target="_blank"` and `rel="noopener noreferrer"`.
- On season rollover, preserve all files in `seasons/` and `data/history/`. Never reuse a prior-week tune code or solution without fresh current-week evidence.
- Unknown facts stay empty in the activity field and are listed in both `missingFields` and top-level `openItems`. Missing evidence is allowed; structural drift is not.
- Before publication run `automation/validate_season.ps1`. Publish only when it prints `STRUCTURE_OK` and the portable build has passed validation/package.
- Publish through `automation/publish_to_github.ps1` on branch `daily-season`; never force-push.
- When `data/project.json.steamGuide.enabled=true`, generate `reports/steam-guide-current.txt` with `automation/render_steam_guide.ps1` after every successful report refresh. Update the existing Steam guide and its single current-week section; never create duplicate weekly sections. Keep the Steam text explicitly Russian and regularly updated, include every current activity in game order, and link prominently to `steamGuide.publicGuideUrl`. If the authenticated Steam edit UI is unavailable, keep the generated file current and report the publication blocker instead of claiming success.
- Keep the generated Steam subsection at or below the project safe ceiling of 4,800 characters. `automation/render_steam_guide.ps1` must report the character count and stop before browser editing if the ceiling is exceeded. Reduce repeated labels, generic no-tune advice, and duplicated caveats; do not drop activities, reorder them, omit specific car/share-code recommendations, or remove the prominent report links at the beginning and end. This prevents Steam error 8 (`Description is too long`), observed at 5,611 characters; the compact 4,066-character version was accepted.
- Treat Steam as a publication target on every daily run, but distinguish substantive text changes from the daily `lastContentUpdate`. After generating the mirror, run `automation/check_steam_guide.ps1`; it compares the substantive mirror with the last browser-verified publication state in ignored local storage. A timestamp-only HTML refresh is not a Steam edit.
- On `STEAM_STATUS=UPDATE_REQUIRED`, do not edit Steam in the unattended heartbeat: send `UpdateRequired` through `automation/send_home_assistant_notification.ps1` and wait for the user to confirm in the `Сводка сезона` chat. On `UP_TO_DATE`, send `UpToDate`; on an incomplete audit/check, send `CheckBlocked`. Use the successful audit timestamp as `RunId` so retries cannot duplicate a push.
- After a user-confirmed Steam replacement, verify the public guide, run `automation/mark_steam_guide_published.ps1`, and then require `automation/check_steam_guide.ps1` to return `UP_TO_DATE`. Never mark content as published before public verification.
- After GitHub Pages and Steam verification, run `automation/collect_publication_metrics.ps1 -RunId <lastContentUpdate>`. Report both current totals and changes since the previous successful metrics snapshot: Steam unique visitors, Steam current favorites, and GitHub guide views from the configured hits.sh API. Include the three deltas in the final chat summary and append them to the single Home Assistant notification. On the first run, explicitly report that a baseline was created; never present the starting totals as newly added views or favorites.
